# Changelog

Notable changes to Valkama, newest release first. Each release says what changed for
its users since the release before it: a few highlights, what broke where something did,
then features, bug fixes and performance improvements, each line linked to the commits
that made it. The layout is
[conventional-changelog](https://github.com/conventional-changelog/conventional-changelog)'s,
and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

The MCP server reports itself as `<release>+<build>`, where the build is a digest
over the modules the running process started with. Two servers from different
checkouts are therefore distinguishable even at the same version.

## [Unreleased]

### Highlights

- Work has a model of its own. A work item is a task, a bug, an improvement, a goal or a
  stage; goals and stages hold work at any depth, are never claimed and, once accepted,
  show what they derive from the work under them: not started, in progress or awaiting
  confirmation. A workflow has a state in each of eight categories — Triage, Deferred,
  Ready, Dev, Review, Done, Blocked and Cancelled — new work starts in Triage, and the
  order work is taken in is computed rather than set by hand.
- The owner decides where agents act alone. A participation setting, for all spaces and
  for each one, says at which points an agent's write waits for the owner's answer and
  at which it goes ahead; Settings has a Participation tab for it, and the Agent decisions
  page lists what agents decided on their own.
- Review asks the owner what to check, and the owner's answer completes the work or
  returns it. A goal or stage with nothing open under it awaits confirmation. Work is put
  off until a day, a time, another item's close or a number of new comments, and comes
  back by itself.
- A planning space holds several projects, one of them its default, and a work item names
  the projects it changes. The context bar chooses a space and then a project, and one
  window creates and configures a space with its projects.
- Valkama attaches each commit an agent's session makes to the task that agent holds,
  through Git hooks that `valkama git-hook install` adds to the global Git configuration,
  and a card lists its commits.
- The new Volumes page shows how much work stands in each category, what each goal took
  and has left, how work flowed and which commits stand on no card. Analytics gains a
  Pauses section on how much of the prompt cache a request read after each length of
  pause.
- Agents read a work item by parts, its card by default, and hear more of the work they
  touch: what happens under the goals they work on, their subagents' writes, what
  Valkama records on its own, and after a resume or a compaction a note of the work they
  hold.
- Upgrading: a 3.0 build refuses the store Valkama 2.9 left until
  `valkama migrate work-model` carries it to schema 25. Run it once, after
  `valkama projects upgrade` and `valkama projects map-items`, with the listener and
  every client session stopped for three minutes; it takes the verified recovery point
  `pre3.0` before its first write. Restart every client session after installing: the
  tool schemas and the handshake change. A 2.9 build refuses the migrated store and reads the upgraded project registry
  as malformed, so going back takes the `pre3.0` snapshot, `valkama projects downgrade`
  and the 2.9 release together; see Breaking Changes.

### Breaking Changes

Valkama 3.0 changes what a work item is, and with it the store, the project registry,
the planning tool schemas and the handshake, once. Tool names stay the same.

**The store.** A 3.0 build opens only a store at schema 25 and migrates none as it opens
it. The store Valkama 2.9 left, at schema 18, or 17 from a 2.9 build before 2.9.0, is
refused with "run `valkama migrate work-model` once" and left as it was; an older store is
refused with "open it with Valkama 2.9 first", with no snapshot and no write. With that,
`migrate planning-model`, the `VALKAMA_CUTOVER` permission and the Board-era conversion are
removed: Valkama 2.9 still carries a store of any earlier schema forward
([3cfc9dd](https://github.com/Muratovnik/valkama/commit/3cfc9dd17a0da81a213f81120424e996638bbf58)). [Migrating a 2.9 store](docs/guides/store-upgrades.md#migrating-a-29-store)
gives the order:

1. `valkama projects upgrade` carries the project registry to inventory format 2 and
   projection schema 4, where a space holds several projects with one default; on a
   machine with no registry it writes an empty one. `valkama projects bind` then binds
   the projects each space holds.
2. `valkama projects map-items --output item-projects.json` writes the file the
   migration reads each task's projects and each commit ref's commits from. Read it
   before migrating: you may add a project to a task, or carry fewer commits.
3. Stop the listener and every agent client, wait three minutes, and run
   `valkama migrate work-model --item-projects item-projects.json`. It refuses before any
   write on a Python whose SQLite is older than 3.47.1 (the service itself still runs on
   SQLite 3.43 or newer), while the store's liveness file shows a server running in the
   last three minutes, on a registry that is not in the new format or does not bind each
   space's project, and on an item-projects file that does not match the store. It then
   takes a verified `pre3.0` snapshot with the pictures beside it and runs every step and
   postcondition in one transaction; `--dry-run` migrates a copy.

Going back is the whole set: stop every process that holds the store, put the `pre3.0`
snapshot and its `.images` folder in place, run `valkama projects downgrade` with the 3.0
build, and only then pin the 2.9 release. Everything written since the migration is lost.

**Agents and the MCP tools.** Restart every client session after installing this release:
a running client keeps the tool schemas, the handshake and the skill it read at startup,
and a client written against 2.9 reads a 3.0 answer wrongly or is refused. A retired word
or argument is refused with `invalid_request` and a text naming what replaces it, before
anything is written; nothing translates it.

| Before 3.0 | From 3.0 |
| --- | --- |
| `kind: "epic"` | `kind: "goal"`, or `"stage"` under a parent |
| a record's `container` and `ready` | `kind` and `workable`; `open`, and `container_state` where `state` is `null` |
| the categories `backlog` and `queued`, the state key `todo` | `triage` and `ready`; `ready` |
| `scope: "epic"` in `get_work_item_chain` and the usage read | `scope: "tree"`, every level under the item |
| `rank` in `update` and `transition` | nothing: the order of work is computed, and a list row carries `queue_order` |
| `get_work_item` with `full: true`; the full record from a `verbose` write and `claim_ready_work_item` | `parts` naming what the work needs; the card by default |
| `claim_ready_work_item` with no `space`, taking from every space | `space`, or `within` naming a goal or stage, else the space whose project root holds the session's folder |
| `create_planning_space` with `project_id` | `name` and an optional `key`; `valkama projects bind` adds projects |
| `refs: [{"kind": "commit", …}]` | `commits: [{"repository": "<project id>", "hash": "…"}]` |
| `update` with `parent: ""` | `move_out` with the `reason` the item leaves its goal or stage for |
| `transition` into a deferred state | `defer` with `until` and `reason` |
| `expired_reason: "task_closed"` and `[task_closed]` | `item_completed` or `item_cancelled`, written by the close, and `[item_closed]` |

The rules a write meets change as well:

- A move into Review needs every step ticked, a summary and `to_check`, what the owner is
  to check (`review_question` otherwise), and asks the owner, whose answer completes the
  item or returns it to Ready. An agent does not complete an item, or take it out of
  Review, while a question to the owner is open on it (`question`); `force` carries
  neither.
- A move into Blocked needs a stated reason: a `blocks` link no longer stands for one. An
  item is never created in a Review, Blocked, Done or Cancelled state (`new_item`).
- A goal or stage does not complete while work under it is open (`children`). Its cancel
  with open work under it is refused with `cancel_list` and the list of what would close,
  and goes through when the same move sends `cancels` with that list's token.
- An agent's write that the owner's participation setting keeps for the owner is not
  made at once: it answers `waits_for_owner` and waits for the owner's answer. An agent's
  cancel of work other live sessions do waits for those sessions as well, answering
  `waits_for_sessions` where the owner is not asked. A step change of a goal or stage
  needs `checklist_reason`, and a `decision` recommends an answer in every required field
  (`[decision]`). Only a person answers a question that carries a `purpose`, and only the
  session that asked withdraws it.
- `claim_ready_work_item` is refused with `queue_off` in a space whose owner hands out
  work by hand. A launch's ending no longer moves its item to Review: the launched agent
  asks for review itself. A lease lapses after three days of silence instead of fourteen,
  unless the owner sets another term.

Over HTTP, a read of one item without `parts`, and every write's answer, still give the
full record. The writes lose `rank` and refuse `parent: ""` and the ref kind `commit` as the
tools do. `GET /api/ref` refuses `kind=commit` and no longer reads `space`;
`GET /api/commit?repository=<project id>&hash=<hash>` shows an attached commit. A module's
operating levels are `global` and `space`, where the second was `project`, and a web
address that named a project alone opens nothing and offers the choice of a space. A finished
item's `closed_at` is when it last entered its finished state, a space of
`GET /api/platform/planning` whose store could not be read has `work_item_count` `null`, an
expired step claim's `checklist_released` detail is the step's text alone, and a launch's
`repository_status` uses the words of a claim's `project_roots`, with `unbound` for a
space that binds no project.

### Highlights

## [2.8.0](https://github.com/Muratovnik/valkama/compare/v2.7.0...v2.8.0) (2026-11-11)

### Highlights

- A new Analytics module says what agent work spent in a period — agent time, tokens and
  a cost estimated at API prices — by account, project, task, executor, role, launch
  class, model, effort and environment, with a CSV download.
- Usage is counted more exactly: a request counts once in the whole store, each stretch
  records the organization, client, effort and adviser it ran under, and stale runs are
  read again in the background.
- «Work» in the rail follows running work, items and sessions alike, with one session
  sign everywhere; a session works while its turn runs.
- Screenshots can be pasted into a card's text, and `@` mentions offer the project's
  Markdown files.
- Upgrading: the store moves through schemas 14, 15 and 16 behind the verified snapshots
  `preschema14`, `preschema15` and `preschema16`, and a 2.7 build refuses it afterwards;
  going back means restoring the snapshot. The first passes after the upgrade read the
  whole usage history again.

## [2.5.0](https://github.com/Muratovnik/valkama/compare/v2.4.0...v2.5.0) (2026-11-05)

### Highlights

- Comments form threads that can be marked resolved, and an answer can carry an own
  option and comments, and be changed.
- A path or a work item's number in a text opens what it names: a Markdown file in
  Valkama's document viewer, beside a card or in a window of its own, another file in
  the editor, an item's card on hover.
- A session opens where it was last open, by a plan the server makes, and Windows
  notifications say when an agent needs you.
- The graph draws each epic as a frame round its work and shows the work an agent is
  doing now.
- Security: nine fixes harden how the desktop app starts terminals and programs, how
  documents are read from a project, and how pages may be framed.
- Upgrading: see Breaking Changes for store schema 10, its `preschema10` snapshot and
  the way back. The hook spool now writes a session start as version 2; an earlier build
  sets such a file aside as `*.rejected`, which `doctor` counts until it is deleted.

### Breaking Changes

- **store:** the first open by this build migrates the store to schema 10 after a verified snapshot labelled `preschema10`, and every existing row keeps its values; a schema-9 build then refuses the store with `StoreTooNewError`, so restart every agent client after pinning this release with `launcher install` ([4d46dde](https://github.com/Muratovnik/valkama/commit/4d46ddee732262626fdd4625a179490dd6444f04))

  To go back, stop every process that holds the store, delete the `-wal` and `-shm` files
  beside it, put the `preschema10` snapshot in its place, and only then pin the earlier
  release; everything written since the upgrade is lost. Pinned first, the earlier
  release reaches every running session within seconds and refuses the store still at 10.
  [Upgrading the store and going back](docs/guides/store-upgrades.md#migrating-an-older-store)
  has the details.

- **requests:** a note no longer stands in for a required field: `answer_work_item_request` and the interface refuse an answer that leaves a required field without a value or an own variant, naming the field; an earlier answer stays as written ([3b9bf97](https://github.com/Muratovnik/valkama/commit/3b9bf973e083f574e3c06ce9581f6c28eebcbabc))
- **planning:** `get_work_item` reads by default the roots of the 5 threads with the latest activity, each with `replies` and `last_reply`, where it gave the 5 newest comments; `comments_after` and `full` still read every comment flat ([d344d20](https://github.com/Muratovnik/valkama/commit/d344d203ca5f0644ba51e6fd572f077669408755))
